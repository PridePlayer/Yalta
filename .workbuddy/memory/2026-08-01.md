### 6. 本地预览/运行方式（关键：否则会"连接断开，重试中…"）
- 现象：只用 `npm run preview`（仅静态托管 dist）打开页面时，前端连同域 `/ws` 找不到后端，会一直"重新连接中…连接断开，重试中…"。
- 根因：游戏是 WebSocket 联机架构，前端 `src/net/client.ts` 连 `ws(s)://<location.host>/ws`；`vite.config.ts` 的 `/ws` 反代（`ws://127.0.0.1:8080`）**只配在 dev server**，preview 不代理。
- 正确启动（两个进程都要在）：
  1. 后端：需 `ws`/`@types/ws`（已加入 dependencies）。后端是 TS，用 esbuild 打包为 CJS（ESM 输出会因 `ws` 的 `require('events')` 报 "Dynamic require not supported"）：
     `node ./node_modules/esbuild/bin/esbuild server/src/index.ts --bundle --platform=node --format=cjs --external:ws --outfile=server-dist/index.cjs && node server-dist/index.cjs`（监听 8080，`/ws` 路径）。
     已固化成 `npm run server` 脚本。
  2. 前端：必须用 **dev server**（而非 preview），因为它带 `/ws` 代理：`npm run dev -- --port 5188 --host`（或 `vite --port 5188`）。
  3. 打开 `http://localhost:5188/` 即可正常连后端、开始游戏。
- 注意：`aiPlayer.ts:149` 原先的 `.find(... .some(...)) ?? ...` 嵌套写法规 esbuild 的 TS 解析器不吃，已重写为 `Set`+`for` 循环形式。
- 端口清理：被占时用 `netstat -ano | grep :5188` 找 PID，再 `taskkill /F /PID <pid>`（GitBash 的 `kill -9` 在 Windows 下杀不掉 vite 进程）。

### 11. 欧洲地图背景图浏览器缓存（省带宽）
- 诉求：2MB 的 `public/photos/europe-map-bg.jpg` 体积大，用户反复打开想走浏览器缓存、别反复占服务器带宽。
- 根因：Vite dev/preview 对 public 静态资源默认 `Cache-Control: no-cache`（每次打开都发校验请求，命中才 304；硬刷新/换浏览器仍会重下整张 2MB）。`public/` 下的文件 Vite 原样拷贝、不加内容哈希，无法用 `immutable` 长期缓存。
- 修复：
  - `vite.config.ts` 新增 `longCacheMapPlugin`（自定义 connect 中间件，对 `/photos/europe-map-bg.jpg` 直接读盘响应），dev 与 preview 均生效，强制 `Cache-Control: public, max-age=31536000, immutable`，确保不被 Vite 默认头覆盖。改成自响应（readFile 后 setHeader + end）而非只 setHeader，避免被 Vite 静态中间件覆盖。
  - `src/App.css` 两处地图 `url('/photos/europe-map-bg.jpg')` 改为 `url('/photos/europe-map-bg.jpg?v=2')`，用版本号做缓存键，将来换图把 `v=2` 改成 `v=3` 即可强制刷新缓存（浏览器按带 query 的 URL 缓存）。
- 验证：重启前端（杀 5188 后 `npm run dev -- --port 5188 --strictPort`）；`curl -sI` 确认地图返回 `Cache-Control: public, max-age=31536000, immutable` + `image/jpeg` + 2041191 字节；旗帜 svg 仍 `no-cache`（未被误伤）；首页 200。
- 注意：此方案只在 Vite dev/preview 下有效。**若将来部署到真实静态主机/CDN**，需在该主机对大图配同样的 `immutable` 头（或改用带内容哈希的导入方式，让任意主机自动长缓存）。

### 12. 修复 App 组件 Hooks 顺序错误（"开局只剩横杠"真正根因）
- 现象：点「以队长身份开局」后页面只剩一条条横杠，控制台报 `App.tsx` 的 "Rendered more hooks than during the previous render"，并提示 Hook 顺序变化（4 个 useSyncExternalStore → 多了 useState）。

- 修复：把全部 Hook（`useState`/`useRef`）提到组件顶部、任何提前 `return` 之前，固定顺序无条件调用。
- 审计同类问题：Grep 全 src 的 Hook 调用，`ActionCard`/`Lobby`/`LogPanel`/`IntelDrawer`/`client.ts` 的 Hook 均在提前 return 之前，`MetricsPanel` 等其余组件无 Hook —— 无同类隐患。
- 验证：`tsc -b` 通过（exit 0）；dev 服务器 5188 存活、App.tsx 正常转译（200）。需用户在浏览器硬刷新（Ctrl/Cmd+Shift+R）清除崩溃态后再试。
